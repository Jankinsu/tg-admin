# Phase 0：最小可行架构设计

> 状态：**设计基线（尚未编码、尚未安全测试）**  
> 目标：保留现有 Debian 13 / Docker Engine 的完整日常管理能力，以双级认证 + 单次提权代替大规模 sudo 命令白名单。

## 1. 确认的需求与边界

- 个人单用户、单台 Debian 13；通过 Telegram 私聊远程操作。
- 任意普通用户权限的 Shell 命令；查看 CPU、内存、systemd、日志。
- **直接管理已有 Docker Engine 上的已有容器**（查询、启停、日志等），不用另建 Rootless Docker。
- 经单次提权后可以管理 Docker、安装服务、部署 Docker Compose、设置 WebUI 端口与宿主机目录。
- AI 可以建议命令，但 **Bot 不直接接受 AI 的自动控制**；用户逐条提交并授权。
- Telegram 是辅助管理入口；网络断连、Bot 异常和关键恢复仍使用 SSH。
- 本方案是**认证优先**而非**命令范围隔离**：一次获准的任意 root 命令可能永久改变系统，这是明确接受的权限能力，不宣称具备 root 沙箱。

## 2. 最小组件和信任边界

```text
手机 Telegram
    │
    ▼
[tg-admin Bot：非 root；消息处理/TOTP L1/会话状态]
    ├── L1 普通请求 ──▶ [root 管理的执行入口] ──降权──▶ tgexec Shell
    │
    └── L2 高权请求 ──▶ [root 管理的单次提权入口]
                                 │
                    自行校验第二组 TOTP + 命令绑定
                                 │
                          单次执行 root 命令
                                 │
                           结果回传 Bot
```

设计决定：

1. Bot 以独立的 `tgbot` 账户运行；不加入 `sudo` / `docker` 组，不拥有 Docker Socket 权限。
2. 普通 Shell 命令在**不同的**受限账户 `tgexec` 身份运行，不继承 `tgbot` 的 Bot Token、TOTP 凭据及管理会话文件。
3. L2 通过一个**root 拥有且不可由 Bot 修改**的最小 Python 特权入口执行；仅该入口拥有使用现有 Docker Engine 的权限。
4. sudoers 只允许 `tgbot` 在**精确路径、无额外命令行参数**下调用两个固定入口（以 `tgexec` 身份执行普通入口，以 root 身份执行特权入口）。具体命令数据经有大小限制的标准输入传输，不支持把用户提供的程序路径作为 sudo 目标。
5. L2 入口自己验证第二认证凭据、请求有效期、请求是否消费过，不能仅信任 Bot 的“已认证”标志。
6. 两套 TOTP 密钥独立，分别由不同权限的进程读取；第二组密钥只由特权入口读取，不能让 `tgexec` 读取。

**非目标**：实现多用户 RBAC、额外 Docker 管理网关、Rootless Docker 迁移、长期 root Shell、持久的 root 交互式终端。

## 3. 用户交互协议（第一版）

```text
/login                        # 使用 L1 TOTP 登录
/logout                       # 退出
/whoami                       # 查看会话状态

/run uptime                   # L1: tgexec 权限
/run systemctl status docker

/sudo systemctl restart nginx # L2: 对这一条完整命令发起独立授权
/sudo docker ps -a
/sudo docker restart nginx
/sudo docker compose -f /srv/stacks/app/compose.yml up -d
```

推荐 **统一使用 /sudo 前缀** 标识高权限操作，而不是根据命令名称猜测是否要提权。用户输入 `/run sudo ...` 不会转化为高权请求，普通身份下应正常失败。

L2 交互：

1. Bot 在有效 L1 会话内接收 `/sudo <完整命令>`，生成唯一请求 ID，回显待执行内容和超时提示。
2. 用户使用与 L1 **不同的**第二个 TOTP 验证器验证码进行本次授权。
3. Bot 将固定命令、请求 ID、身份上下文、验证码一起提交给特权入口；特权入口**独立核验** TOTP、请求字段、时间与重放记录。
4. 验证成功后，本次请求原子性地标记为已消费，再执行一次命令；失败或超时不执行。
5. 返回 exit code、stdout/stderr（经过截断与敏感输出控制）；每次新的 `/sudo` 都必须重新授权，**不提供 sudo 缓存会话**。

### L2 验证码通道的现实取舍

**第一版优先通过 Telegram 私聊收取第二组 TOTP，保持手机端操作简单、无需额外公网入口。** 该验证码必须只用于当前待处理请求，Bot 接收后尽快删除消息（如 Telegram API 允许），不得写日志。两组验证密钥独立，校验逻辑由 root 入口负责。

但 Telegram Bot 私聊并非端到端加密：如果 Bot 本身被控制，恶意代码可能截获这次验证码并影响命令绑定。因此**该方案不提供针对“Bot 进程已被攻破”的强独立授权保证**；尤其不能宣称与独立、可信的命令确认界面等价。

如果后续要提高这一威胁模型的保障，可升级为独立 HTTPS / Passkey 授权页面，并在该页面直接展示由特权入口保存的完整命令，由用户核对。**这属于未来增强，不阻塞首版开发。**

## 4. 单次提权请求的数据契约（草案）

```json
{
  "version": 1,
  "request_id": "random-128-bit-id",
  "telegram_user_id": 123456789,
  "chat_id": 123456789,
  "created_at": "2026-11-23T08:00:00Z",
  "command": "docker restart nginx",
  "otp": "123456"
}
```

- 上例是假数据；真实 ID、口令、用户信息不能写入仓库。
- 输入大小设置上限；校验 JSON 字段类型、长度、请求时间、身份是否为配置的允许值；不反射记录 `otp`。
- 入口使用 root 所有的持久化状态记录 L2 TOTP 最近成功时间步及已消费请求 ID；避免同一验证码在同一时间窗口内被再次用于其他命令。必须使用锁/事务保证并发下的**先消费、后执行**。
- 入口根据提交的**完整命令字节**建立摘要并登记审计，不能先确认一条命令再执行修改后的另一条。
- 不在 shell 命令字符串中拼接验证码、Token 或其他秘密。
- 执行阶段用显式 `/bin/sh -c` 或 `/bin/bash -lc`，清理环境变量，设置固定工作目录、超时与资源约束；这是**刻意允许的单次任意命令权限**，不是命令白名单。
- 验证和执行逻辑只接受本地受权调用，不开放监听公网的 root HTTP 服务。

> 实现前需考虑**客户端请求不能自行决定服务器信任的创建时间**。可靠实现应由特权组件本地创建/登记待执行请求，然后只接受与该记录匹配的授权；上面的 JSON 是交互字段示意，不应直接把客户端自报的时间、命令或身份当作可信授权事实。

## 5. 需要在编码时落实的细节

| 问题 | 最小设计决策 |
| --- | --- |
| 谁管理 Telegram Token | `tgbot` 独立配置，权限为仅其可读 |
| 谁持有 L1 TOTP 密钥 | `tgbot`，用于普通会话 |
| 谁持有 L2 TOTP 密钥 | root 特权入口独占可读 |
| L1 会话 | 15 分钟绝对超时、5 分钟空闲超时，失败尝试限速 |
| L2 授权 | 一次验证码 + 单条锁定命令 + 60 秒请求窗口，不支持批量授权 |
| 普通命令 | `tgexec` 用户执行，与 Bot 私密文件隔离 |
| Docker 操作 | 通过 L2 入口调用现有 rootful Docker Engine |
| 输出 | stdout/stderr/exit code；有长度上限，可用文件回传较长输出 |
| 长时间命令 | 超时/取消需要终止整个进程组，防止留下子进程 |
| 交互命令 | 首版非交互执行，不支持 `sudo` 密码提示、TTY 编辑器 |
| 本地并发 | L2 初版串行，禁止同一请求重复运行 |
| 命令确认 | 向用户完整显示将执行的命令；密码不显示；执行参数不得在确认后变化 |
| 网络失联 | 已开始执行的命令可能继续运行；审计和状态必须可查 |
| 重要底线 | 不自动改写现有 Docker 配置，不在安装/卸载时删除容器或数据卷 |

### 关于 sudoers 的具体含义

sudoers **不是**用户的每条 `sudo docker ...` 命令都要逐项放行；它只准许 `tgbot` 启动固定的特权入口。该入口可以在 L2 验证成功后执行任意 root 命令——这是明确的能力与风险取舍。

生产实现须校验实际二进制路径、所有权、目录权限、解释器和 Python 导入路径；不能让 `tgbot` 替换入口脚本、依赖包或读取 L2 密钥。**严禁**直接配置 `tgbot ALL=(ALL) NOPASSWD: ALL`。

## 6. MVP 验收用例

- [ ] 未授权 Telegram 账户发送 `/login`、`/run`、`/sudo` 均无法进入管理流程。
- [ ] L1 认证成功后 `/run uptime` 返回正确输出与退出码。
- [ ] `/run` 无法读取 Bot Token、两组 TOTP 密钥或获取 Docker Socket。
- [ ] L2 未验证时，`/sudo docker ps -a` 不得执行。
- [ ] L2 验证成功后，仅指定的 `/sudo docker restart <已有容器>` 执行一次。
- [ ] 重放验证码、重放请求、替换命令、过期请求均不得执行。
- [ ] 并发发送同一授权请求，不会执行两次。
- [ ] 现有 Docker 容器可以查询、启停，不必迁移。
- [ ] 一次新容器部署可映射宿主机 WebUI 端口，并收到完整退出状态。
- [ ] 安装、更新或卸载 Bot 不影响现有 Docker 容器和数据卷。

## 7. Phase 1 的最小代码切片

1. 项目骨架、配置模板、systemd 开发环境，秘密不入库。
2. Telegram 私聊消息处理、固定 User ID / Chat ID 白名单。
3. L1 TOTP 注册、验证、会话状态和限流。
4. 受限 `tgexec` 执行入口，回传 stdout/stderr/退出码。
5. 为 Phase 2 定义并测试 L2 请求和校验接口，**不提前给 Bot root 权限**。

在 Phase 1 验收前不在真实服务器启用 L2 提权入口。后续逐步实现 Phase 2、已有 Docker 管理和服务部署。
